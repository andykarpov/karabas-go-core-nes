# План развития NES-ядра Karabas Go

Цели:

1. Мапперы и исправления из upstream (MiSTer `NES_MiSTer`, MiST `mist-devel/nes`).
2. Сохранения картриджа: PRG-RAM на батарейке, эмуляция EEPROM, flash-сейвы (`.sav`).
3. Снапшоты (save states): сохранение и загрузка состояния в любой момент.

Затрагиваются четыре репозитория:

| Репозиторий | Что меняется |
|---|---|
| `karabas-go-core-nes` | ядро: память, загрузчик, мапперы, CPU/PPU/APU, сохранения, снапшоты |
| `karabas-go-modules` | `kg_mcu` (`ENABLE_IMG`), новый `kg_bk_ram`, команды сохранений, тесты |
| `karabas-go-firmware` | создание и подключение `.sav` / `.ssN`, flush, OSD, `docs/protocol*.md` |
| `karabas-go-tools` | поля `core.json` и заголовка ядра: `make_core.py` и Go-версия `makecore`, `core_structure*.txt` |

## 0. Исходное состояние

Ядро — FPGANES (strigeus) почти без изменений. MiSTer NES вырос из этого же кода, интерфейс `MultiMapper` у них родственный.

- Используется только `MA[18:0]` и младший байт `MD[7:0]`: PRG и CHR ROM по 256 КБ (`memorycontroller.v`). На платах 4 МБ SRAM (2M x 16) и 32 МБ SDRAM.
- PRG-RAM — 8 КБ в BRAM (`ram8k`), однопортовая, снаружи недоступна.
- `GameLoader.v` разбирает только iNES 1.0: 8-битный маппер, нет NES 2.0 (сабмаппер, размеры RAM), бит батарейки `ines[6][1]` не используется, игры с трейнером отклоняются.
- Звука с картриджа (expansion audio) нет.
- MCU-линк — старая копия `mcu.vhd`: канал FPGA→MCU есть только для ответа на `CMD_CAPS`, file mounter (`CMD_IMG_*`) не поддерживается.
- Мапперы (`mmu.v`): 0–5, 7, 9–11, 13, 15, 28, 34, 41, 47, 64, 66, 68, 69, 71, 79, 105, 113, 118, 119, 158, 206, 228, 232, 234.
- Ресурсы (go / mini / minig): LUT 26 / 33 / 33 %, RAMB16 34 из 52.

Главное ограничение для upstream: **XST не понимает SystemVerilog**, а мапперы, PPU и APU MiSTer написаны на SV. Всё переводится на Verilog-2001 (см. 3.1). VHDL-части upstream (если есть) XST берёт как есть.

## Ф1. Память и загрузчик

### 1.1. SRAM 4 МБ

`MemoryController`: полная адресация `MA[20:0]` + выбор байтовой полосы (`MWR_N[1:0]`, `MRD_N[1:0]`), байтовый адрес 22 бита. Внутреннее адресное пространство маппера расширить (сейчас 22 бита, `[21:20]` — регион).

Раскладка (предварительно):

| Адрес SRAM | Размер | Содержимое |
|---|---|---|
| `0x000000` | 2 МБ | PRG ROM |
| `0x200000` | 1 МБ | CHR ROM |
| `0x300000` | 64 КБ | CHR-RAM (до 32 КБ) + резерв |
| `0x310000` | 64 КБ | PRG-RAM / NVRAM (сохраняемая, до 64 КБ: MMC5, SXROM 32 КБ) |
| `0x320000` | 64 КБ | память мапперов: EEPROM, ExRAM, внутренняя RAM N163 и т.п. (если не в BRAM) |
| `0x340000` | 256 КБ | буфер снапшота (Ф6) |
| `0x380000` | 512 КБ | резерв: FDS (4 стороны по 65500 Б), NSF |

- CPU RAM 2 КБ и VRAM 2–4 КБ остаются в BRAM. PRG-RAM переезжает в SRAM, BRAM освобождается.
- Арбитраж SRAM: сейчас CPU и PPU ходят в такте `nes_ce == 0`. Загрузчик, `kg_bk_ram` и DMA снапшотов получают свободный такт (например `nes_ce == 2`), так что NES не тормозит.
- SDRAM 32 МБ пока не нужна: всё помещается в SRAM, а асинхронная SRAM проще по таймингу. Возможное применение позже: несколько слотов снапшотов в памяти, rewind.

### 1.2. GameLoader

- NES 2.0: 12-битный номер маппера, сабмаппер, MSB размеров PRG/CHR ROM (байт 9), PRG-RAM / PRG-NVRAM (байт 10), CHR-RAM / CHR-NVRAM (байт 11), регион (байт 12: NTSC / PAL / Dendy).
- **Бит батарейки** `ines[6][1]` (и NVRAM из NES 2.0) — в флаги.
- Трейнер (512 Б): загружать в `$7000` PRG-RAM, а не отклонять игру.
- Флаги маппера расширить до 64 бит, совместимо с раскладкой `flags` MiSTer, чтобы портированные мапперы подключались без переделки.
- Для iNES 1.0 без NES 2.0: размер PRG-RAM по умолчанию 8 КБ; известные исключения (SXROM, MMC5) — по мапперу и размеру ROM.
- Контрольная сумма ROM при загрузке (CRC-32 или сумма) — для заголовка снапшота (Ф6).

## Ф2. Сохранения картриджа (`.sav`)

Сейв — сырой дамп backup-памяти картриджа (как у MiSTer и FCEUX, файлы должны быть совместимы — проверить на реальных `.sav`). Механизм общий для всех видов backup-памяти:

- PRG-RAM на батарейке (Zelda, FF, Dragon Warrior, Kirby);
- EEPROM 24C01 / 24C02 / X24C01 (Bandai 16, 157, 159) — Ф4;
- flash (UNROM-512 / 30, GTROM / 111 — самопрограммирование) — Ф4.

Транспорт — существующий file mounter (`CMD_IMG_*`, 512-байтные секторы, суммы, повторы, burst, `sync` файла в простое). Сейв — это «образ», который прошивка подключает сама, без участия пользователя.

### 2.1. Протокол (сверить коды с `src/config.h`)

| Код | Направление | Формат | Смысл |
|---|---|---|---|
| `48` `CMD_BK_MOUNT` | FPGA → MCU | `48 i v_i` (i = 0..3: размер в секторах, LE), затем `48 80 kind` | Ядро просит подключить файл backup-памяти. `kind`: 0 = `.sav`, 1..N = слот снапшота `.ssN`. Размер 0 — отключить. |
| `47` `CMD_IMG_FLUSH` | MCU → FPGA | `47 slot 00` | «Запиши всё грязное сейчас». |
| `47` `CMD_IMG_FLUSH` | FPGA → MCU | `47 slot 01` | Готово: грязных секторов нет. |
| `F7` `CMD_CAPS` | FPGA → MCU | бит 3 caps | Ядро поддерживает `CMD_IMG_FLUSH` / `CMD_BK_MOUNT` (старые ядра прошивка не ждёт). |

Размер решает ядро, а не прошивка: только ядро знает правила маппера (EEPROM 256 Б, SXROM 32 КБ). Прошивке не нужно дублировать разбор мапперов.

### 2.2. `karabas-go-modules`: `kg_bk_ram`

Общий модуль (пригоден и для других ядер):

- вход: секторный интерфейс file mounter (как `img_sdc`), порт памяти backup-области (SRAM через арбитр или BRAM), размер;
- при подключении образа: читает N секторов в память, держит `bk_busy` (CPU в reset / пауза);
- битовая карта грязных секторов: выставляется при записи CPU / маппера в backup-область;
- автосохранение: грязные секторы пишутся через ~1–2 с после последней записи;
- `CMD_IMG_FLUSH`: немедленно записать всё и ответить «готово»;
- запись не мешает игре (идёт в свободных тактах SRAM).

Плюс: декодирование `47` в `kg_mcu_img`, очередь `48`, бит caps, команды в `kg_mcu_cmds.vh`, тесты в `sim/mcu` (подключение, грязные секторы, flush, потеря кадра, отсутствие ответа).

### 2.3. `karabas-go-firmware`

- Поля заголовка ядра: каталог сейвов (по умолчанию `<dir>/saves`), номер img-слота под сейв, слот под снапшот. Место — резерв после `FILE_POS_SPI_FREQ`.
- Обработчик `CMD_BK_MOUNT`: имя `<save_dir>/<имя игры без расширения>.sav` (или `.ssN`), создать каталог, открыть или создать файл нужного размера (заполнить нулями; `img_mount` сейчас открывает только существующие), подключить в слот обычной последовательностью `CMD_IMG_SLOT` / `CMD_IMG_SIZE`. Длинные имена (exFAT, `getName`).
- `CMD_IMG_FLUSH` с ожиданием ответа (таймаут ~1 с) перед: загрузкой другой игры, сменой ядра, перезагрузкой, входом в USB MSC. Только если ядро объявило бит caps.
- OSD: всплывающее «Saved» / «Save error».
- `docs/protocol.md` и `docs/protocol.ru.md`, `config.h`.

### 2.4. `karabas-go-tools`

`core.json`, например:


Добавить в `make_core.py` и Go-`makecore`, описать в `core_structure*.txt` и README (ru / en).

### 2.5. Ядро

- `kg_bk_ram` на область PRG-RAM, бит батарейки и размер из `GameLoader` → `CMD_BK_MOUNT` после загрузки игры.

## Ф3. Мапперы из MiSTer (перевод на Verilog)

### 3.1. Способ перевода

1. Первый проход — `sv2v` (SV → Verilog-2005), затем ручная чистка под XST: никаких SV-конструкций, объявлений в безымянных блоках, `'1`; tri-state шины `*_b` заменить мультиплексором в диспетчере (или проверить, что XST сам превращает их в логику).
2. Проверка эквивалентности: исходный SV в verilator против переведённого Verilog, одинаковые стимулы (записи CPU, адреса PPU), сравнение всех выходов каждый такт — по образцу `karabas-go-modules/sim/eq`.
3. Прогон тестовых ROM маппера в симуляции и на железе.
4. Контроль LUT / таймингов после каждой группы.

Порты шины снапшотов (Ф6) **переводить сразу**, даже если они пока не подключены, чтобы не переделывать мапперы второй раз.

### 3.2. Диспетчер

Заменить `MultiMapper` на перевод `cart.sv` MiSTer (64-битные флаги, сабмапперы, звук картриджа, `prg_from_ram`, сигналы PPU для MMC5). Существующие мапперы strigeus перестают быть нужны по мере переноса.

### 3.3. Исправления существующих мапперов

- **MMC1:** игнорировать запись в соседних циклах CPU (RMW; Bill & Ted); бит отключения PRG-RAM; SUROM / SOROM / SXROM (PRG A18 и банки PRG-RAM через CHR-регистры: DW III/IV, FF I/II).
- **MMC3:** поведение IRQ (старое / новое) по сабмапперу; MMC6 (4/1, StarTropics 1/2).
- **MMC5:** режимы ExRAM, вертикальный сплит, умножитель `$5205`, 8x16 спрайты, звук (Castlevania III, Just Breed).

### 3.4. Новые мапперы (порядок по охвату библиотеки)

1. Konami VRC2 / VRC4 (21, 22, 23, 25), VRC6 (24, 26) + звук, VRC1 (75), VRC3 (73).
2. Namco 163 / 175 / 340 (19, 210) + звук, варианты Namco 108 (88, 95, 154).
3. Sunsoft: 5B-звук для 69 (Gimmick!), Sunsoft-3 (67), 89, 93, 184.
4. Bandai FCG (16, 153, 159), Datach (157) — с EEPROM (Ф4).
5. Jaleco / Irem / Taito: 18, 32, 33, 48, 65, 80 / 207, 82.
6. Дискретные и homebrew: 30 (UNROM-512), 111 (GTROM), 140, 152, 180, 185, 94, 97, 70, 87.
7. Мультикарты: 225, 226, 227, 229, 231, 255, 58, 62.

## Ф4. EEPROM и flash

- Модель I2C EEPROM 24C01 / 24C02 / X24C01 (по MiSTer) с памятью в BRAM или SRAM, подключённая к `kg_bk_ram` как backup-область: Bandai 16 / 159 / 157 (Dragon Ball Z, SD Gundam).

## Ф5. CPU / PPU / APU из MiSTer

Нужен и для точности, и для снапшотов (шина состояния есть в модулях MiSTer).

- Перевод PPU и APU на Verilog по 3.1; CPU — то, что в MiSTer (Ф0, п. 5).
- Звук картриджа: микширование VRC6 / VRC7 / N163 / 5B / MMC5 / FDS.
- Регионы: NTSC / PAL / **Dendy** (из NES 2.0 или OSD) — тайминги CPU / PPU / APU и видеовыход (`vga.v`, framebuffer).
- Совместимость с текущим видеотрактом (framebuffer, OSD, HDMI / VGA) и входом (`hid_parser`).
- Проверка: blargg cpu / ppu / apu тесты, список игр.

## Ф6. Снапшоты (save states)

### 6.1. Ядро

- Шина состояния (как в MiSTer): у каждого модуля (CPU, PPU, APU, маппер, звук картриджа) набор регистров, читаемых / записываемых по индексу.
- Сохранение: по команде пауза на границе кадра (CPU на границе инструкции) → DMA в буфер SRAM (`0x340000`): регистры по шине + память (CPU RAM, VRAM, OAM, палитра, PRG-RAM, CHR-RAM, память маппера) → игра продолжается → буфер пишется в файл в фоне.
- Загрузка: `CMD_BK_MOUNT kind=N` → чтение файла в буфер → проверка заголовка → пауза → восстановление → продолжение.
- Заголовок снапшота (первый сектор): сигнатура `KGSS`, версия формата, id ядра, номер маппера / сабмаппер, контрольная сумма ROM, размер. Не та игра или другая версия формата — отказ с сообщением в OSD.
- Объём: регистры — сотни байт, память — до ~110 КБ (с PRG-RAM 64 КБ и CHR-RAM 32 КБ) → до ~220 секторов.

### 6.2. Прошивка

- Файлы `<save_dir>/<игра>.ss1` .. `.ss4`, подключаются по `CMD_BK_MOUNT` в отдельный img-слот (`state_slot`).
- OSD: выбор слота (1–4), триггеры «Save state» / «Load state» с горячими клавишами (например F5 / F8), всплывающие сообщения.
- Скорость записи FPGA → MCU классическими кадрами — порядка единиц мс на сектор, т.е. ~1–2 с на снапшот в фоне. Если мало — burst-чтение (caps бит 2, «planned» в протоколе).

### 6.3. Модули и tools

- `kg_bk_ram` должен уметь работать со вторым слотом и с буфером снапшота (или отдельный простой модуль «буфер ↔ секторы»).
- `core.json`: `state_slot`, OSD-элементы; описание в `make_core`.

## Порядок и зависимости

```
Ф0 ─┬─ Ф1 ─┬─ Ф2 (.sav на текущих мапперах)
    │      └─ Ф3 (мапперы MiSTer) ─ Ф4 (EEPROM / flash)
    └────────────────── Ф5 (CPU/PPU/APU) ─ Ф6 (снапшоты)
```

- Ф2 можно сделать и выпустить до Ф3: сейвы сразу работают для большинства игр.
- Ф3 и Ф5 можно вести параллельно, но Ф6 требует обоих (шина состояния во всех модулях).
- Протокол (2.1) меняется один раз в Ф2 так, чтобы Ф6 не требовал новых команд.

## Открытые вопросы

- Влезут ли VRC7 (OPLL) и полный набор мапперов в LUT XC6SLX25 (сейчас 26–33 %) — проверять после каждой группы в Ф3.
- Совместимость `.sav` с MiSTer для EEPROM-мапперов (порядок байт, размер).
- Нужна ли SDRAM (слоты снапшотов в памяти, rewind) — решить после Ф6.
